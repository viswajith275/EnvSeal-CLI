EnvSeal CLI · v6.1.0 · Rust · MIT · Offline

Secrets that live
in your Git repo.
Encrypted. Branch-aware. Mergeable.

EnvSeal isn't a .env replacement or another encryption wrapper. It's a Git-native secrets workflow — your vault is a single encrypted file that travels with git pull, switches with git checkout, resolves with git merge, and is reviewed in pull requests like any other artifact. No cloud. No accounts. No shared master password.

Install
$ curl -sSfL https://raw.githubusercontent.com/viswajith275/EnvSeal-CLI/master/scripts/install.sh | bash
> winget install --id viswajith275.envseal -e
$ cargo build --release

The Git-native promise

If your team already uses Git for code review, history, and branch hygiene, your secrets inherit every one of those workflows on day one — without a dashboard, a web app, or a single byte leaving your machine.

What you're probably doing now

DATABASE_URL=postgres://localhost:5432/app STRIPE_SECRET=sk_live_51H8xQ2... JWT_SIGNING_KEY=9f2c... AWS_ACCESS_KEY_ID=AKIA... # gitignored, DM'd around, one git add . # away from sitting in your Git history # forever. Bots are already scanning.

The problem isn't that .env is bad. It's that .env was never designed to travel — and everything around it (.env.example, shared docs, Slack DMs) is a workaround for that.

03 — The Git-Native Workflow

Onboard a teammate
with a pull, not a password.

This is the whole pitch in two columns. You set up the vault and commit it. Your teammate pulls, runs their app, and it just works — same keys, correct branch, zero DMs, zero shared secrets, zero screenshots of a .env in Slack.

💻
On your machine
01
envseal init --local
Creates the encrypted vault file in your repo.
02
envseal git-setup
Installs the pre-commit shield and registers the merge driver.
03
envseal set DATABASE_URL
Prompts for the value without echoing it. Stored encrypted.
04
git add .envseal && git commit -m "seal secrets"
Commit the encrypted vault like any other file.
05
git push
The vault travels with the code. No extra channel needed.
Git
🧑‍💻
On their machine
01
git clone … (or git pull)
The encrypted vault arrives with the repo. Nothing else to fetch.
02
envseal recipient id
Prints their public key. They send it to you once — then never again.
03
# you run, once: envseal recipient add @them
They're now authorized for every current and future commit.
04
envseal run -- npm start
Secrets decrypt into the child process. The app boots.
05
git checkout feature/stripe-v2
Secrets switch with the branch. No manual swapping, ever.

Why this matters more than the encryption

Most secrets tools give you a stronger lock and then ask you to change how your team works. EnvSeal changes nothing about your Git workflow — it just makes the vault a first-class citizen of it. That means PRs, git blame, code review, and history all apply to your secrets the same way they apply to your code. And because the vault is encrypted for recipients, a leaked repo is not a leaked secret.

04 — Branch-Aware Secrets

The vault knows
what branch you're on.

envseal run calls git rev-parse --abbrev-ref HEAD behind the scenes. If a stored tag matches your current branch name, it's applied automatically. Base secrets fill the gaps. No manual swapping. No stale config. No accidentally testing experimental code against production.

main base
DATABASE_URL→prod-db.internal
STRIPE_PUBLIC_KEY→pk_live_…
applies everywhere
staging tag
DATABASE_URL→staging-db.internal
overrides base on staging
inherits STRIPE_PUBLIC_KEY
feature/stripe-v2 tag
STRIPE_SECRET→sk_test_…
overrides base on this branch
inherits DATABASE_URL

Prefer separate files? Use -e staging to target .staging.envseal instead of relying on branch tags.

$ envseal set --tag staging DATABASE_URL
05 — Git Guardrails

One command installs
the guardrails.

envseal git-setup writes a pre-commit hook and registers a custom merge driver. The hook bounces raw plaintext back before it reaches Git history. The driver resolves vault conflicts without a diff editor in sight — including a fixed, non-interactive rule for CI runners.

.env
.envseal
pre-commit barrier
$ envseal git-setup

On a plaintext stage

[envseal] COMMIT REJECTED: Staged plaintext .env file(s) detected: → .env Unstage them, or run `envseal init --local` to create an encrypted .envseal vault.

Merge driver resolves conflicts

# Keep current branch's values git -c envseal.merge.strategy=ours merge feature-branch # Accept incoming branch's values git -c envseal.merge.strategy=theirs merge feature-branch # Set a fixed rule for CI runners git config envseal.merge.strategy theirs

07 — Ephemeral Runtime

Secrets exist for exactly
as long as the process.

envseal run decrypts into the child process's memory and injects it as environment variables. Nothing hits disk. When the process exits, the secrets are gone.

envseal run -- npm start
▸ injecting DATABASE_URL → child process env
▸ injecting STRIPE_SECRET → child process env
▸ injecting JWT_SIGNING_KEY → child process env
> app@1.0.0 start
> node server.js
listening on :3000
Process exited. Secrets gone.
0 plaintext bytes on disk.
click to inject · click to evaporate

Ephemeral execution

$ envseal run -- npm start

The safe default. Secrets live only in the child process and evaporate on exit.

Interactive shell

$ eval "$(envseal load)"

For debugging only. Once loaded, secrets stay in your shell until you close it. Prefer run.

08 — Scoped CI & Global Vault

Borrow exactly what CI needs.
For exactly as long as it needs it.

Never paste your personal SSH or Age key into a CI runner. A CI token is a temporary, scoped channel into the vault — limited by tag, by key, and by an expiration. Separately, your personal configuration lives outside any repository in a Global Vault.

Scoped CI token

envseal token --tag prod \ -o ./ci.token --exp 3600 \ STRIPE_SECRET DATABASE_URL
✔ token written to ./ci.token scoped to: STRIPE_SECRET, DATABASE_URL expires: 3600s (CLI-enforced)

Short-lived tokens keep your long-term identity out of runners. Prefer --exp 3600 or less. Expiry is enforced by the CLI, not by cryptography — see the candor section below.

Global developer vault

$ envseal --global init
$ envseal link myapp ✔ linked myapp → global vault
$ envseal --global run -- ./deploy.sh

For personal scripts and one-off secrets that don't belong to any repo. One system-wide vault, attached to as many local directories as you like.

09 — Engineering Candor

Things worth knowing
before you trust any encryption tool.

Cryptography is very good at math and very bad at knowing whether you actually meant to leave the front door open. A few honest caveats, stated plainly.

01
Removing someone doesn't erase what they already saw.
envseal recipient rm stops a person from decrypting future commits. But Git history is permanent — anyone who cloned earlier still has old encrypted commits and could decrypt them with a key they already hold. If someone leaves under bad terms, rotate the actual credentials too, not just the vault. Removing their access is taking away the house key after they've already made a copy.
02
envseal rotate protects the future, not the past.
Rotation generates a fresh key and re-encrypts the current state of the vault. It does not retroactively re-encrypt old Git commits — those snapshots stay encrypted under the old key. If a leaked token ever let someone extract the underlying material, they could still decrypt old commits. The only thing that actually neutralizes a leaked secret is changing the secret itself. So: rotate the vault and go rotate the API keys or database passwords at the source.
03
Token expiry is enforced by the CLI, not by cryptography.
The --exp flag is a runtime check performed by EnvSeal itself. Because everything is offline, there's no server refusing an expired token — a sufficiently determined attacker with the raw payload could bypass the clock check. Treat expiry as a guardrail, not a cryptographic guarantee. If a CI runner is ever compromised, don't wait for the token to expire: rotate the vault and the underlying secrets immediately.
04
If you're your only recipient, you're also your only point of failure.
EnvSeal has no "forgot password" button, and it never will — that's the entire point of zero-trust design. If your laptop dies, gets stolen, or falls in a lake, there's no cloud backup, no support ticket, and no admin override. Treat your Age/SSH identity like a seed phrase: back it up outside the repo, and consider adding a second recipient (a spare key on another device, or a trusted friend) purely as a recovery path.
✅ Where EnvSeal genuinely wins
  • Git-native by design. The vault is a file in your repo, not a parallel system you have to remember to sync.
  • Free and offline. No accounts, no cloud, no telemetry. Works on a plane or behind a corporate firewall.
  • Branch-aware. The only option in its class that switches secrets automatically on git checkout.
  • Reviewable. Every secret change is a commit. PRs, git blame, and history all apply.
⚠️ Where it's honestly not the best fit
  • No web dashboard, no audit log. If you need to see who accessed what and when, you want a cloud tool.
  • No non-technical UI. Everyone on the team touches a terminal. If that's a dealbreaker, look at Doppler or Infisical.
  • You can lock yourself out permanently. Zero-trust means zero recovery. Back up your key.
  • Kubernetes / cloud-KMS shops. If you're deep in GitOps, SOPS is a more natural fit than bolting EnvSeal on.

For a student or small-team codebase, the trade-off is easy: you're giving up a GUI you probably wouldn't use anyway, in exchange for something free, offline, and native to the Git workflow you're already using.

10 — Command Reference

The whole CLI,
at a glance.

If you've used Git, this will feel familiar. Every command is a single verb, and most of them have a natural Git analogue you already know.

Core

envseal git-setup [--init]
Register the Git merge driver and pre-commit shield.
envseal set [-g GROUP] [-t TAG] KEY
Store a secret (prompts without echoing input).
envseal get [-g GROUP] [-t TAG] [--token TOK] KEY
Print one decrypted value (use sparingly).
envseal run [-g GROUP] [-t TAG] [--token TOK] -- CMD
Run a command with secrets injected. Alias: exec.
envseal load [-g GROUP] [-t TAG] [KEYS...]
Print shell exports for eval. Prefer run.
envseal list [-g GROUP] [-t TAG]
List key names without revealing values. Alias: ls.
envseal edit [-g GROUP] [-t TAG]
Edit key/value pairs in your default editor.
envseal remove [-g GROUP] [-t TAG] [--force] [KEY]
Delete a key, tag, or group. Alias: rm.

Bind a global vault group to the current directory.
envseal clear

11 — Optional Shell Integration

Load into your shell —
only if you really want to.

envseal run -- <CMD> is the recommended usage, because secrets only exist for the life of that process. If you'd rather load variables into your interactive shell session for debugging, add one of these wrappers.

# ~/.bashrc or ~/.zshrc envseal() { if [ "$1" = "load" ]; then for _arg in "$@"; do if [ "$_arg" = "--help" ] || [ "$_arg" = "-h" ]; then command envseal "$@" return fi done eval "$(command envseal "$@")" else command envseal "$@" fi }
# ~/.config/fish/config.fish function envseal if test "$argv[1]" = "load" if contains -- --help $argv; or contains -- -h $argv command envseal $argv else eval (command envseal $argv) end else command envseal $argv end end
# $PROFILE function envseal { param( [Parameter(ValueFromRemainingArguments = $true)] [string[]]$EnvsealArgs ) $exe = Get-Command envseal -CommandType Application -ErrorAction SilentlyContinue | Select-Object -First 1 -ExpandProperty Source if (-not $exe) { Write-Error "envseal: not found on PATH. Install: winget install viswajith275.envseal" return } if ($EnvsealArgs.Count -gt 0 -and $EnvsealArgs[0] -eq 'load') { if ($EnvsealArgs -contains '--help' -or $EnvsealArgs -contains '-h') { & $exe @EnvsealArgs return } & $exe @EnvsealArgs | Invoke-Expression } else { & $exe @EnvsealArgs } }

Heads up about envseal load

Once variables are in your interactive shell, they stay there until you unset them or close the terminal — and they can leak into any subsequent command you run. Prefer envseal run -- ... for almost every real workflow.

Troubleshooting quick hits

SEAL TAMPERED

Ed25519 signature verification failed.
# The .envseal file was edited manually
# or corrupted outside the tool.

Fix: git checkout -- .envseal

Access Denied

Identity not authorized for this env.
# Your key isn't registered in this vault.

Fix: Ask a teammate to run
envseal recipient add @you

Token Scope Mismatch

Token was minted for a different tag.
# You're running against 'staging'
# but the token only has 'prod' keys.

Fix: Re-mint for the correct tag.
envseal token --tag staging ...

Command not found

envseal: command not found
# The install script falls back to
# ~/.local/bin on restricted systems.

Fix: restart terminal or run `hash -r`
export PATH="$HOME/.local/bin:$PATH"

Common Questions

Q
Can I use EnvSeal with Docker / Docker Compose?
Yes. Build your image normally, then at runtime do something like

envseal run -- docker compose up

or inject only the keys you need directly into the container environment.
Q
Does it work with monorepos?
Yes. You can keep one .envseal at the root, or use the -e / profile mechanism to manage separate per-package vaults within the repository.
Q
What happens if two people add different secrets at the same time?
EnvSeal registers as a native Git merge driver, so most merges resolve silently in the background. If two contributors change the same key to different values, it stops and asks you to pick a side via --ours or --theirs.
Q
Can I still keep a local .env for personal overrides?
Yes, but the pre-commit shield will block you from accidentally committing it. Treat personal overrides as truly local and never stage them.
Q
I forgot my private key and I'm the only recipient. What now?
This is not a bug EnvSeal can fix — it's a backup problem. The vault is designed so that only holders of the recipient keys can decrypt it, and there is no override, no cloud recovery, and no support ticket that will get it back. If you still have the identity file somewhere (another machine, a backup drive, a password manager), restore it and you're fine. If you don't, the vault is a locked box with no key.
